# KeeleSepp CRM v1 — передача состояния работ

Актуально: 27.08.2026, Europe/Tallinn
Репозиторий: `zakutailopavel-cyber/keelesepp`
Рабочий интерфейс: `haldus.html`
Текущая ветка: `codex/v1-terms`

## Граница задачи

Работа продолжается над первой CRM. `crm-v2/` в этом проходе не изменялся. Live Classroom остаётся последним этапом и не входит в текущий приоритет. Тарифы скрыты, отдельная модель поставщиков не нужна; для языковой школы используется обычный блок расходов.

Главный принцип v1: не переписывать архитектуру одним большим изменением и не ломать действующую Firebase-логику. Новые административные операции должны использовать точные ID, защищённые серверные маршруты, обязательную причину и журнал изменений.

## Что было сделано ранее

- канонические связи ученика и родителя через Firebase Auth UID;
- безопасное объединение дублей с preview, переносом зависимостей и архивированием старых карточек;
- центр исправления данных для потерянных связей, групповых уроков, счетов, аккаунтов и неверных дат;
- расходы с чеками, исправлением и аннулированием без удаления истории;
- закрытие финансового месяца, экспорт и корректировки закрытого периода;
- финансовый и бухгалтерский реестр, точные связи уроков, счетов и платежей;
- поиск, фильтры и выгрузки учеников, счетов и расходов;
- библиотека материалов и предпросмотр без скачивания;
- первичная диагностика ученика.

### Действия для неоприходованных уроков

В `LessonPaymentRegisterPanel` добавлена колонка `Toimingud`:

- `Arve` создаёт счёт только для выбранного урока через `addInvoice(studentId, {lessonIds:[lessonId]})`;
- `Tasuline` назначает `late_cancel_billable` для пропуска;
- `Tasuta` назначает `free` для завершённого урока или `cancelled_on_time` для пропуска;
- `Kanna maha` назначает `written_off`;
- кнопки блокируются на время операции;
- счёт требует отдельного подтверждения, а изменение статуса — существующую обязательную причину;
- серверная модель, финансовый аудит и административная часть не обходятся и не дублируются.

Изменение передано через существующую цепочку `App → AccountingRegisterView → LessonPaymentRegisterPanel`.

### Тема проведённого урока больше не обязательна

- урок из календаря можно сохранить в дневник со статусом `Toimunud`, не заполняя тему;
- поле явно подписано как необязательное;
- если тема не введена, сохраняется пустая строка, а существующие списки и финансовые документы используют предусмотренное нейтральное название `Tund` / `Toimunud tund`;
- остальные данные урока, пакетный учёт и финансовая логика не изменены.

### 27.08.2026 — системное исправление учёта уроков

Учёт проведённых уроков больше не опирается на несколько независимых записей из браузера. Добавлен защищённый серверный маршрут `POST /lessons/journal`, который одной транзакцией:

- проверяет роль администратора или назначенного преподавателя;
- требует точный `studentId` существующей карточки и больше не создаёт новые индивидуальные записи с техническим `studentId: ext`;
- сохраняет дневниковую запись, статус календаря и старые счётчики ученика согласованно;
- использует постоянный ID из расписания, даты и ученика, поэтому повторное нажатие, повтор запроса или другая вкладка не создают дубль;
- записывает отдельные статусы `Toimunud`, `Puudus_p` и `Puudus_eta`;
- для одного проведённого повторяющегося занятия меняет только выбранную дату, не всю будущую серию;
- создаёт для проведённого урока финансовый статус `unbilled`, чтобы запись сразу попадала в очередь выставления счёта;
- запускает идемпотентный пакетный учёт и явно ставит `needs_attention`, если движение пакета не удалось завершить.

Удаление дневниковой записи перенесено в защищённый маршрут `POST /lessons/journal/delete`. Он проверяет права, закрытый финансовый период, связь со счётом и пакетом, а затем одной транзакцией удаляет запись, восстанавливает календарь и корректирует старый счётчик. Удаление серии календаря блокируется, если от неё зависят несколько дневниковых записей.

## Production hotfix 27.08.2026: сохранение дневника после объединения ученика

Симптом в production:

- при сохранении дневника для `Milan Grozovski`, 27.08.2026 в 13:00, интерфейс показывал общее сообщение `Päeviku salvestamine ei õnnestunud. Proovi uuesti või eemalda failid.`;
- запрос `POST /lessons/record` завершался с HTTP 409;
- точный ответ сервера: `Schedule entry belongs to another student`.

Точная причина:

- после объединения дублей Милана архивные карточки остались в подписке `students`, что правильно для сохранения истории;
- календарная запись уже ссылалась на основную карточку ученика;
- форма дневника выбирала ученика только через первое совпадение имени;
- при одинаковых именах могла быть выбрана архивная карточка, и в запрос попадал другой `studentId`;
- серверная проверка связи календаря и ученика правильно блокировала такую запись. Проверка не ослаблялась.

Исправление:

- в `haldus-shared.js` добавлен единый `resolveStudentRecord(students, record)`;
- сначала используется точный `studentId` календарной записи;
- ссылка `mergedIntoStudentId` приводит архивную карточку к основной;
- совпадение по имени допускается только для одной активной канонической карточки, неоднозначное имя не угадывается;
- эта логика подключена к полной форме дневника и к быстрому завершению урока;
- вместо общей подсказки удалить файлы интерфейс теперь показывает конкретное действие для ошибок связи ученика, финансового периода, выставленного счёта, прав преподавателя и размера вложений;
- `financeApi` пишет безопасный структурированный warning с путём, статусом и ограниченным текстом ошибки без тела запроса и персональных данных;
- версия интерфейса обновлена до `KeeleSepp CRM · 27.08.2026.3`.
